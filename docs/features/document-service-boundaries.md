# 문서·PDF 기능의 상태와 서비스 경계

문서 작업공간은 탭·선택 문서·정리본 선택 상태를 소유한다. `App.tsx`는
`useDocumentWorkspace`의 공개 동작과 선택 결과를 다른 기능에 연결한다.
정리본을 가져오는 요청과 그 요청의 취소 수명은 문서 기능 안에서 관리한다.

PDF 상태는 다음 훅이 각자 생성하고 소유한다. `usePdfController`는 이들을
조합하며 기존 `annotation`, `document`, `ocr`, `study`, `translation`, `view`
계약을 제공한다. 기존 소비자가 쓰는 타입은 해당 진입점에서 재수출한다.

| 소유 모듈 | 책임 |
| --- | --- |
| `use-pdf-document-state.ts` | 문서 열기 확인, 페이지 위치, 뷰어 참조 |
| `use-pdf-view-state.ts` | 배율, 테마, 펼침 방식, 검색 UI 상태 |
| `use-pdf-annotation-state.ts` | 주석 설정·목록·실행 취소 상태 |
| `use-pdf-ocr-state.ts` | OCR 작업·진행률·취소·엔진 준비 상태 |
| `use-pdf-study-state.ts` | 문제·책갈피·학습 작업 상태 |
| `use-pdf-translation-state.ts` | 번역 진행·취소·오류 상태 |

문서 편집 훅은 저장 함수를 조립 계층에서 전달받는다. `DocumentSaveQueue`는
디스크 쓰기의 순서와 마지막 저장 내용 캐시, 종료 시 진행 중인 저장을 기다리는
책임을 소유한다. 편집 훅은 초안·실행 취소·화면 전환과 늦은 응답의 적용 여부를
관리한다. 저장 실패 뒤에도 다음 저장을 수행할 수 있고, 해결되지 않은 마지막
저장 오류는 종료 대기에서 드러나야 한다.

Python의 문서 서비스는 `api_server`, `api_modules`, `api_request_handler`를
import하지 않는다. API Mixin은 요청을 서비스에 연결하고, 서비스는 전달받은
설정 조회 함수와 기능별 동작만 사용한다.

| 소유 모듈 | 책임과 전달받는 의존성 |
| --- | --- |
| `documents/material_file_policy.py` | 지원 형식과 기존 작업 폴더·외부 파일 허용 경계 |
| `documents/material_sources.py` | 문서 내부 이미지·Markdown 링크의 표시용 경로 변환 |
| `documents/material_file_service.py` | 문서 읽기·저장. 저장 폴더 조회, PDF 추출·페이지 수 조회, 저장 후 알림을 전달받음 |
| `documents/pdf_study_service.py` | 읽던 페이지 기록과 현재 저장 폴더의 학습 DB 선택·캐시. 페이지 읽기·수정은 서비스 잠금으로 직렬화 |
| `documents/material_search_service.py` | 검색 방식·개수 제한·모델 준비 정책. 저장 루트와 검색·준비 동작을 전달받음 |

`bootstrap`의 레지스트리는 첫 사용 시 기능 서비스를 한 번 생성한다. 문서·학습·검색
하위 서비스도 해당 소유자가 첫 사용 시 한 번 연결한다. 자료 작업공간은 읽기·저장,
목록·캐시, 파일 관리, 문제 생성 인스턴스를 별도로 소유하며 단순 파일 읽기가
파일 관리·목록 코드를 초기화하지 않는다. 파일 관리와 직접 읽기·저장은 같은
문서 서비스 인스턴스를 사용한다. 생성은 잠금으로 직렬화하고 종료 후 생성을
거절한다. 형식별 파서는 해당 형식을 읽거나 저장할 때 불러온다. 설정 변경은 조회
함수를 통해 다음 작업에 반영된다. 학습 저장 폴더가 바뀌면 해당 폴더의 DB를
선택하고, 이전 폴더의 기록을 덮어쓰지 않는다. 전체 조립과 종료 경계는
[애플리케이션 구조](application-architecture.md)에 정리되어 있다.

기존 Mixin 메서드와 경로·표시용 변환 함수의 공개 import는 호환 진입점으로
유지한다. API 경로, 응답 필드, 외부 파일 허용 목록, 저장 파일과 DB 형식은
이 경계 분리로 바뀌지 않는다.

## 검증 기준

- 프런트엔드는 `ails-frontend`에서 `node node_modules/typescript/bin/tsc -p tsconfig.app.json --noEmit`으로 검사한다.
- 저장 큐는 빠른 연속 저장, 실패 후 재시도, 종료 대기 중 추가된 저장을 확인한다.
- 서비스는 임시 저장 폴더에서 Markdown·노트북 왕복, 상대 링크, 허용된 외부 파일과 거부되는 경로를 확인한다.
- 읽던 페이지의 동시 갱신과 저장 폴더 변경 후 학습 세션 복원을 확인한다.
- 실제 `ApiState`와 HTTP 요청으로 파일 읽기·저장과 로컬 API 토큰 검사를 확인한다.
- Electron에서 외부 PDF·Markdown 열기, 기존 창 재사용, 편집 저장과 창 종료를 확인한다.

DOCX 편집기는 초기 불러오기와 실행 취소 기준점 생성 뒤 지연 도착한 렌더
알림을 실제 편집으로 기록하지 않는다. 마지막 문서 값과 비교하여 텍스트·서식
변경을 알리고, 여백처럼 별도 옵션에 속한 변경은 해당 명령에서 알린다.

Office 열기는 인증된 GET 읽기 경로를 사용하고 기존 POST 경로도 지원한다.
두 경로는 같은 파일 허용·형식 검사를 거쳐 같은 응답을 반환한다. GET 응답은
저장하지 않으며 다음 열기에서 외부 변경을 다시 읽는다. 복구 저장소는 임시
저장·백업을 쓸 때 만들고, 단순 읽기는 디렉터리를 만들지 않는다.

시트 엔진의 화면 연결은 `sheets-ui-controller.ts`가 소유한다. Univer의 기존
편집기와 플러그인을 유지하며 화면 크기와 준비 상태에 맞춰 캔버스를 연결한다.
숨김 화면의 지연 연결과 폐기 시 예약 작업 해제도 이 모듈의 책임이다.
메뉴 병합과 Rendered 단계의 변경 알림은 인스턴스별 `sheets-menu-manager.ts`가
동기적으로 묶는다. 메뉴 데이터의 즉시 조회는 유지하고 작업이 끝날 때 화면을
갱신하며 별도 타이머를 만들지 않는다. 시트 명령은 자신의 문서를 대상으로
실행하고, 검색 제공자는 첫 검색 시 준비하여 Steady 단계의 고정 대기를 피한다.
검색 대화상자 영역은 첫 화면 구성 전에 등록하여 늦은 UI 등록과 최초 열림
이벤트 사이의 유실을 막는다. 외부 CSV·XLSX의 모듈 선행 로딩은 Electron의
정적 자산 게이트웨이가 담당하며 편집기 생성·문서 상태는 이 계층에 남는다.
`OfficeEngine.presentationElement`는 형식별 실제 본문 표시 영역을 제공한다.
CSV·XLSX는 내부 텍스트 편집용 캔버스 대신 준비된 시트 캔버스를 반환하고,
공통 표시 관찰자는 화면 안에 드러났는지를 확인한다.
DOCX는 문서 캔버스, HTML은 Monaco의 코드 줄 생성 후 코드 영역을 반환한다.
HTML 미리보기의 로드 완료와 코드 본문 표시는 별도 기준이다.

서비스 검사의 런타임 데이터와 `APPDATA`, `LOCALAPPDATA`는 임시 폴더로
격리한다. 창 성능 검사는 임시 문서·Electron 프로필·런타임 설정을 사용하며,
기본 시스템 앱 데이터 경로의 조회가 없는 완전 격리 실행으로 간주하지 않는다.
테스트 프로세스와 임시 테스트 스크립트는 검증 후 정리한다.
